# Python Expense Tracker — Complete Version 1 Study Guide

## 1. What problem does it solve?

You record spending once, then retrieve it later, see monthly category totals,
and export it for a spreadsheet. The application runs in a terminal. It is not
a website and does not use a cloud service. Its currency is Nigerian naira.

The important learning goals are command parsing, validation, functions, classes,
SQL, persistent storage, exact monetary arithmetic, and automated testing.

## 2. Start with a safe practice database

Open a terminal in the downloaded or cloned project directory. Use a separate
practice file so you can freely experiment:

```sh
python -m expense_tracker --db practice.db add 1500 food --date 2026-10-12 --note "Lunch"
python -m expense_tracker --db practice.db add 800 transport --date 2026-10-12
python -m expense_tracker --db practice.db list
python -m expense_tracker --db practice.db summary --month 2026-10
python -m expense_tracker --db practice.db export practice.csv
python -m unittest discover -s tests -v
```

On Windows, `py` can replace `python`. You must be inside the repository folder,
because Python needs to find the `expense_tracker` package. The `--db` option goes
before the command. Most command-specific options go after it.

Expected total: NGN 2,300.00. Adding the same commands again creates additional
records, so the total will increase. There is no automatic duplicate detection.

## 3. The files and their responsibilities

| File | Responsibility |
| --- | --- |
| `expense_tracker/__init__.py` | Marks the directory as a Python package |
| `expense_tracker/__main__.py` | Terminal interface: reads commands and prints results |
| `expense_tracker/core.py` | Validation, money conversion, persistence, summaries, export |
| `tests/test_tracker.py` | Checks behavior using isolated temporary databases |
| `README.md` | Quick overview for someone opening the repository |
| `docs/NEXT_STEPS.md` | Future milestones; not implemented features |
| `.gitignore` | Keeps local databases, exports, and generated bytecode out of commits |

Separating interface and storage means a future API could call the same business
operations without needing to parse terminal commands. The current design is small;
a larger service would need clearer service/repository boundaries.

## 4. Trace one expense all the way through

Consider `python -m expense_tracker --db practice.db add 1500 food`.

1. Python finds the package and executes `__main__.py`.
2. `main()` builds an `ArgumentParser`. Its subparsers define supported commands.
3. `parse_args()` turns text into a namespace: command is `add`, amount is the
   string `1500`, category is `food`, and date defaults to the local current date.
4. `ExpenseStore(args.db)` initializes the database schema if necessary.
5. `store.add()` converts naira into kobo and validates the inputs.
6. The amount is stored as integer `150000`, not as floating-point `1500.0`.
7. SQLite executes a parameterized INSERT and generates an integer record ID.
8. The transaction commits if the operation succeeds; failures roll back.
9. `add()` returns the ID. The interface prints `Added expense #1.`

That trace is the most useful thing to understand first. Try changing the input
and predicting the values before you run it.

## 5. Functions you should understand

### `money_to_kobo(value)`

A function accepts an input and returns an output. This function converts
`"12.50"` to integer `1250`. `Decimal` represents decimal money exactly, while
binary floating-point cannot represent every decimal fraction exactly. The
function rejects NaN, infinity, zero, negatives, excessively large values, and
fractional kobo. It does not silently round `1.001` to `1.00`.

`raise ValueError(...)` stops the normal path and communicates a bad input.
`raise ... from exc` preserves the original conversion exception as its cause.
The maximum single expense is NGN 10,000,000,000.00.

### `format_money(kobo)`

Divides by 100 using Decimal and formats two decimal places with comma separators.
The `f` string embeds the computed amount inside a readable string.

### `valid_date(value)` and `valid_month(value)`

A regular expression checks the required shape. The date library checks the actual
calendar. Shape alone would accept February 30, so both checks matter. A month is
validated by appending `-01` and asking Python to parse that date.

### `csv_safe(value)`

Spreadsheet applications can interpret text beginning with `=`, `+`, `-`, or `@`
as a formula. For user-controlled notes and categories, this function prefixes
an apostrophe when such a prefix is detected after whitespace. That is a
conservative export defense; CSV behavior can differ between spreadsheet tools.

## 6. Classes, `self`, and the database

`ExpenseStore` is a class: a definition for objects that manage a particular
expense database. `self.path` is state belonging to that instance. `self` means
the particular object on which a method was called.

`__init__` runs when you construct an instance. It creates the parent directory
and executes `CREATE TABLE IF NOT EXISTS`. That statement is safe to run on later
starts because it preserves the existing table. It does not migrate an old schema
if the table structure changes in a future version.

The `expenses` table contains five columns:

| Column | Meaning |
| --- | --- |
| `id` | Unique integer identifier |
| `amount_kobo` | Positive integer monetary amount |
| `category` | Trimmed, lowercase category such as `food` |
| `spent_on` | Validated date stored as `YYYY-MM-DD` text |
| `note` | Optional description, at most 500 characters |

`sqlite3.Row` allows `row["category"]` instead of remembering numeric column
positions. The `with` block handles transactions. The connection helper also
closes connections after their operation.

## 7. Understand every storage operation

`add()` validates before inserting. The SQL has four `?` placeholders, and a
separate tuple supplies values. Never replace these with string interpolation.
A note containing SQL-looking text remains a note, rather than an SQL command.

`list()` optionally filters by `substr(spent_on,1,7)`, the first seven characters
of the date. Dates sort correctly as strings in this consistent format. Results
are newest first; record ID breaks ties. This simple month filter can be improved
with date ranges and an index when the dataset becomes large.

`summary()` gets matching rows and accumulates amounts in a dictionary. For each
category, `totals.get(category, 0)` means use its previous total, or zero if it is
not present. Two food expenses of 10 and 20 kobo become `{ "food": 30 }`. Sorting
makes the printed category order predictable.

`delete()` removes only a matching ID. `rowcount` tells whether a record existed.
The CLI requires `--yes`; the database operation itself does not ask questions.
There is no undo, so practice with disposable records.

`export()` writes a header and one CSV row per selected expense. `csv.writer`
handles commas and quotes, so a note containing a comma is not split incorrectly.
The destination file is overwritten. Export can include personal information;
share only a deliberately prepared sample.

## 8. Error handling and testing

The interface catches `ValueError`, operating-system file errors, and SQLite
errors. `parser.error()` prints the problem and exits with status 2. This gives
scripts a machine-readable indication that the command failed.

Each test gets a new temporary directory and database. Tests cannot damage your
real expenses. They verify exact money conversion, rejected amounts and dates,
persistence after reopening, monthly filters and totals, SQL-looking notes,
CSV escaping, missing IDs, deletion confirmation, and actual CLI behavior.

Run tests from the project root. A green result means these checked cases passed;
it does not prove the absence of all bugs or production readiness.

## 9. A realistic nightly study sequence

Night 1: run the practice commands and explain what the application does in your
own words. Learn imports, strings, integers, and function calls.

Night 2: trace `add` from CLI input to stored row. Explain each validation check.

Night 3: read `list` and `summary`. Practise loops and dictionaries by calculating
category totals on paper, then compare your answer to the program.

Night 4: examine three tests, deliberately break one calculation, observe the test
failure, then restore it. Keep those experiments local.

Night 5: make one small improvement yourself and add a test for it. Good options:
print a count with summaries, reject a category consisting of punctuation, or add
a command that shows a single expense by ID.

## 10. Interview questions and honest answers

**Why SQLite?** It offers persistent relational storage without a separate server,
which suits a single-user local application. A deployed multi-user service has
different requirements.

**Why integers for money?** Whole kobo can be added exactly. Decimal handles input
conversion and formatting. Currency rules would need redesign for other currencies.

**How is SQL injection avoided?** User values are bound as SQL parameters. The
query structure is fixed by the application.

**What would you change for a web service?** Add HTTP routing, request schemas,
authentication and per-user authorization, migrations, deployment configuration,
logging, and API integration tests. None of those features are implemented yet.

**How did you build it?** Development used AI assistance. Explain the parts you
studied, the changes you actually made, and the tests you actually ran. Do not claim
users, independent implementation, or performance measurements without evidence.

## 11. Readiness check

You understand this version well when you can run it unaided, explain the add
trace, predict monthly totals, identify where data is stored, describe an error,
and make a small change with a passing test. Reading the guide is the beginning;
working with the code is how you check that understanding.
